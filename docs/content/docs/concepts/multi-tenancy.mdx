Trove doesn't isolate tenants for you. It has no notion of a current tenant, enforces no quotas and filters nothing by tenant on its own. What it does give you are building blocks: a `TenantKey` field on the extension's metadata models, middleware scopes and routing functions that can look at your request context, and per-store separation in the Forge extension.

<Callout type="warn">
Earlier versions of this page described automatic tenant stamping from an `X-Subject-ID` header and per-tenant quota enforcement on `Put`. Neither exists. `trove.ErrQuotaExceeded` is only returned when a storage backend itself reports a quota or rate limit.
</Callout>

## Tenant Keys in the Metadata Store

The extension's metadata models (`github.com/xraph/trove/extension/model`) carry a `TenantKey`:

```go
type Bucket struct {
    ID        string
    Name      string
    TenantKey string
    // ... other fields
}

type Object struct {
    ID        string
    BucketID  string
    Key       string
    TenantKey string
    // ... other fields
}

type Quota struct {
    TenantKey    string
    UsedBytes    int64
    LimitBytes   int64
    ObjectCount  int64
    LimitObjects int64
    UpdatedAt    time.Time
}
```

Nothing fills these in automatically. If you keep metadata there, set `TenantKey` yourself and filter with the store's list option:

```go
objects, err := metaStore.ListObjects(ctx, bucketID,
    store.WithTenantKey("tenant-abc"),
)
```

`ListBuckets(ctx, tenantKey)` filters buckets the same way. The `trove_quotas` table and `GetQuota`, `SetQuota` and `UpdateQuotaUsage` exist for you to build quota checks on, but no Trove code reads them. See [Grove Store Layer](/docs/integration/grove-store).

## Middleware Scoping by Tenant

A `ScopeFunc` sees the request context, so you can apply middleware to one tenant's traffic. Put the tenant in the context yourself, before calling `Put` or `Get`:

```go
import "github.com/xraph/trove/middleware"

type tenantKey struct{}

tenantScope := &middleware.ScopeFunc{
    Fn: func(ctx context.Context, bucket, key string) bool {
        tenantID, _ := ctx.Value(tenantKey{}).(string)
        return tenantID == "acme-corp"
    },
    Desc: "tenant(acme-corp)",
}

// Encrypt only Acme Corp's data with their key.
t, _ := trove.Open(drv,
    trove.WithScopedMiddleware(tenantScope,
        encrypt.New(encrypt.WithKeyProvider(acmeKeyProvider)),
    ),
)
```

<Callout type="info">
The resolver caches pipelines by bucket and key, not by context. A `ScopeFunc` that answers differently for two tenants writing the same bucket and key can get the cached answer from the first call. Keep tenant data under tenant-specific keys or buckets so the cache key differs.
</Callout>

### Per-Tenant Encryption Keys

A `KeyProvider` also receives the context, so one encrypt middleware can return a different key per tenant:

```go
type TenantKeyProvider struct {
    vault VaultClient
}

func (p *TenantKeyProvider) Key(ctx context.Context) ([]byte, error) {
    tenantID, _ := ctx.Value(tenantKey{}).(string)
    return p.vault.GetKey(ctx, "trove/keys/"+tenantID)
}

t, _ := trove.Open(drv,
    trove.WithMiddleware(
        encrypt.New(encrypt.WithKeyProvider(&TenantKeyProvider{vault: vc})),
    ),
)
```

## Routing Tenants to Backends

`trove.WithRouteFunc` decides the backend from the bucket and key, so a naming convention lets you keep tenants on separate backends:

```go
t, _ := trove.Open(shared,
    trove.WithBackend("acme", acmeDriver),
    trove.WithRouteFunc(func(bucket, key string) string {
        if strings.HasPrefix(bucket, "acme-") {
            return "acme"
        }
        return ""
    }),
)
```

With the Forge extension you can go further and give a tenant its own named store (`stores:` in config), each with its own driver and metadata database.

## Authorization

`extension/hooks.NewWardenHook` gives you an HTTP middleware for the REST handler that checks each request against Warden, using the `X-Subject-ID` header as the subject. It authorizes a subject against a resource type and action. It doesn't know about tenants, and you have to make sure the header comes from your own authentication layer. See [Ecosystem Integration](/docs/integration/ecosystem).

## What You Have to Build

| Need | What Trove provides | What you add |
|------|---------------------|--------------|
| Tenant on each record | `TenantKey` fields in the metadata store | Set it when you write metadata |
| Tenant-filtered listings | `store.WithTenantKey`, `ListBuckets(ctx, tenantKey)` | Call them; `t.List` on the driver is never filtered |
| Quotas | `trove_quotas` table and store methods | The checks and the usage updates |
| Per-tenant encryption | `ScopeFunc`, context-aware `KeyProvider` | Put the tenant in the context |
| Separate backends | `WithRouteFunc`, multi-store mode | A naming or config convention |
| Access control | The Warden hook | A trusted subject header and tenant-aware policies |
